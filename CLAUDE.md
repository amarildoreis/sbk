## 1. O que estamos construindo

Uma plataforma web premium para a **SBK Capital**, empresa especializada em antecipação de recebíveis, operações estruturadas, crédito e soluções financeiras personalizadas para o mercado de **Factoring/FIDC**.

O produto nasceu como um painel em Power BI — já maduro, com mais de 60 medidas DAX, 9 fontes SQL e um conjunto de regras de negócio testadas em produção. Ele está sendo reconstruído como **aplicação web nativa**, conectada diretamente a um banco **SQL Server**, com dois pilares:

1. **Dashboard executivo e operacional** — exposição de carteira, comportamento de títulos, comissões, liquidez, risco, vencidos, relatórios analíticos e consultas operacionais.
2. **Interação por IA (RAG)** — uma área conversacional, no espírito de um ChatGPT financeiro, que responde perguntas em linguagem natural sobre os dados do cliente, usando este documento e o banco SQL Server como fonte de verdade.

O objetivo não é entregar "mais um sistema de gestão de recebíveis". O objetivo é o **efeito UAU**: um produto com aparência de software enterprise sofisticado, forte presença visual, acabamento impecável, navegação intuitiva e arquitetura pronta para crescer — em nível visivelmente acima do que o mercado de fomento mercantil está acostumado a ver.

### 1.1 Relação com a WBA — parceira potencial, não concorrente

O **WBA** (wba.com.br) é o sistema mais usado hoje no segmento por empresas de Factoring, Securitizadoras e FIDCs: no mercado há mais de 30 anos, modular, robusto em integrações (bancos, bureaus, custodiantes) e consolidado como ERP do setor. É também, hoje, quem opera o sistema e detém a base de dados da SBK Capital — ou seja, a fonte SQL Server deste projeto (seção 16) roda sobre a infraestrutura de um cliente WBA.

**Isso não faz da WBA uma concorrente. É o contrário: é uma parceira em potencial.** A plataforma que estamos construindo não substitui o ERP da WBA — ela se conecta aos dados que já existem nele e entrega uma camada analítica e de IA que o WBA hoje não oferece. Duas frentes comerciais futuras decorrem disso:

1. **SaaS complementar** — oferecer esta plataforma diretamente aos clientes da WBA (empresas de factoring/FIDC), como camada analítica + IA sobre os dados que eles já têm no WBA.
2. **Parceria com a própria WBA** — a WBA passa a oferecer este produto aos seus próprios clientes, rentabilizando com o serviço.

Isso muda o objetivo de design: não estamos tentando "vencer" o WBA em completude de ERP (cadastro, borderô, cobrança, integrações bancárias — isso continua sendo função do WBA). Estamos entregando **o que falta**: uma experiência visual e analítica premium, com IA conversacional nativa, que se encaixa ao lado do WBA em vez de competir com ele.

| Eixo | WBA (ERP operacional, parceiro de dados) | SBK Capital (camada analítica premium + IA) |
|---|---|---|
| Papel no ecossistema | Sistema de gestão/operação (cadastro, borderô, cobrança, integrações bancárias) | Camada complementar de analytics + IA sobre os mesmos dados |
| Percepção visual | ERP tradicional, denso, utilitário | Produto premium, "efeito UAU", visualmente irresistível |
| Interação com dados | Telas de consulta e relatórios fixos | Camada analítica + IA conversacional (RAG) em linguagem natural |
| Arquitetura | Legado modular consolidado | Web nativa, moderna, API-first, pronta para escalar |
| Modelo comercial futuro | Fonte de dados / parceiro de distribuição | SaaS oferecido a clientes WBA, ou white-label via a própria WBA |

Toda decisão de design e de produto deve reforçar esse posicionamento: somos o complemento premium e inteligente que se conecta à base de um cliente WBA (ou de qualquer outro ERP do setor) — não uma alternativa que compete pelo mesmo espaço.

## PARTE I — Produto, Design e Experiência

### 3. Contexto de negócio

A SBK Capital atua com antecipação de recebíveis, financiamentos, operações estruturadas, investimentos e crédito personalizado. A plataforma deve refletir esse contexto com linguagem visual corporativa, segura, sofisticada e confiável — transmitindo inteligência financeira, solidez institucional, agilidade operacional e tecnologia aplicada ao negócio.

A interface deve comunicar, **sem precisar explicar**:

- confiança
- controle
- inteligência analítica
- velocidade operacional
- clareza na leitura de risco
- sofisticação institucional
- tecnologia orientada ao crédito

### 4. Referência visual do projeto

Os prints de referência do produto atual (Power BI) mostram um dashboard branco, corporativo, com forte uso de azul escuro institucional, áreas bem delimitadas, filtros no topo, botões segmentados, blocos analíticos, números grandes e tabelas operacionais densas.

Essas referências são **base estrutural de negócio**, não limite estético. O novo produto deve manter a clareza e organização desses layouts, mas **elevar fortemente** o nível de design, profundidade, microinterações, sofisticação visual e percepção de valor.

### 5. Sistema visual

**Estética geral:** a interface deve ser **premium, memorável e impecável**. Nada pode parecer genérico, improvisado, simples demais ou com "cara de dashboard admin padrão".

**A experiência visual deve transmitir:**
produto enterprise de alto valor · sofisticação institucional · segurança e credibilidade · tecnologia financeira moderna · clareza de leitura · refinamento visual · impacto comercial.

**O que evitar:**
aparência de template pronto · visual infantil · excesso de cores sem hierarquia · excesso de brilho gratuito · poluição visual · cards sem refinamento · tabelas com cara de sistema antigo · soluções comuns de backoffice sem personalidade.

#### 5.1 Paleta principal (oficial — paleta_sbk_v2)

Esta é a paleta de cores **oficial e definitiva** do projeto. Toda variável de cor no código (CSS custom properties, tokens do design system, Tailwind config etc.) deve derivar diretamente destes valores — não aproximar, não "chutar de olho".

| Token | Hex | Papel no produto |
|---|---|---|
| `--color-azul-marca` | `#12183F` | **Exclusivo da logomarca** — reproduzir a identidade visual (badge/ícone da SBK, painel de marca em telas de login/splash). Não usar como cor de UI geral |
| `--color-azul-escuro` | `#1A2347` | Cor primária institucional de UI — sidebar, topbar, headers, textos de maior peso, botões primários |
| `--color-azul-medio` | `#2E3F7F` | Estados ativos, links, hover, destaque e profundidade (equivalente ao "azul petróleo/aço" do briefing original) |
| `--color-cinza-prata` | `#C8CDD6` | Bordas, divisores, fundos neutros de apoio, texto secundário sobre fundo escuro |
| `--color-verde-escuro` | `#2D5C3A` | Positivo/aprovado forte — títulos pagos, situação regular, indicadores de saúde da carteira |
| `--color-verde-claro` | `#4A8C5C` | Positivo secundário — variações leves de sucesso, disponível, tags e badges |

**Regra de uso:** `--color-azul-marca` (`#12183F`) é o tom exato da logomarca oficial (arquivo `Logomarca.jpeg`) e só deve aparecer onde a marca está sendo reproduzida literalmente — o badge/ícone da SBK, painéis de marca em telas de login, splash screens, materiais institucionais. Todo o restante da interface (sidebar, topbar, botões, textos) usa `--color-azul-escuro` (`#1A2347`). São dois tons propositalmente próximos, não intercambiáveis: um é "cor de marca", o outro é "cor de produto".

Branco e off-white (`#FFFFFF` / `#F7F8FA` sugeridos) seguem como fundo padrão das superfícies, como já era no briefing original.

`--color-vermelho-risco` e `--color-ambar-alerta` foram calibradas para dialogar com a paleta v2 (mesma saturação contida, mesmo tom "institucional desaturado") — não são vermelho/âmbar "de alerta de trânsito", são versões sóbrias, coerentes com o restante da paleta.

Roxo/violeta sutil deixa de ser cor padrão da paleta; só deve ser considerado no futuro se surgir uma necessidade funcional muito específica sem cor livre disponível nesta tabela.

**Estrutura principal esperada:**

### 7. Motion e interatividade

**Deve ter:** hover premium · transições suaves · sensação de profundidade · resposta visual elegante ao foco e clique · animações discretas, porém presentes · entrada de elementos com fluidez · sensação de produto vivo.

**Não deve ter:** animações nervosas · exagero de movimento · efeitos chamativos sem propósito · lag visual · teatralidade excessiva.

**Regra:** toda interação deve parecer pensada por um product designer sênior.

### 8. Componentes esperados

- **Botões e segmentações** — premium, estados ativos muito claros, boa leitura, feedback elegante no hover, sensação tátil refinada.
- **Filtros** — aparência limpa e poderosa, selects e inputs com excelente acabamento, foco muito bem resolvido, organização clara.

### 12. Interação por IA com dados (RAG)

A área de IA é uma parte estratégica do produto — não um recurso secundário. Ela deve permitir perguntas em linguagem natural sobre os dados da empresa, gerando respostas, análises, relatórios resumidos e explicações de indicadores com base no SQL Server, **usando a Parte II deste documento como base de contexto/regras de negócio**.

**Essa área deve transmitir:** inteligência · confiabilidade · clareza · contexto de negócio · apoio à tomada de decisão.

**Exemplos de uso esperados:**
- "Quais sacados concentram maior risco hoje?"
- "Qual cedente aumentou mais a exposição nos últimos 30 dias?"
- "Explique por que os títulos vencidos subiram este mês."
- "Mostre um resumo da carteira por comercial."
- "Quais clientes têm maior atraso médio?"
- "Qual o valor total de comissão do comercial X neste mês?"

**Regra de UX:** a resposta da IA deve parecer executiva, útil e orientada a negócio — nunca apenas técnica ou um despejo de dados brutos.

**Requisito de fundação para o RAG:** como definido na seção 5.13 da Parte II, esta documentação (nomenclatura, entidades, regras de negócio, relacionamentos) é a fonte de contexto candidata para alimentar o sistema de RAG. Nomes de colunas, medidas e regras devem permanecer descritivos e consistentes, evitando abreviações ambíguas, para facilitar indexação e recuperação semântica.

> **Arquitetura combinada com o cliente em 2026-07-18 — 3 caminhos, RLS obrigatório antes do roteador.** Toda pergunta passa primeiro pelo contexto de permissão do usuário logado (a mesma trava de Comercial/Cedente/Sacado da seção 21.17 — nunca reimplementada à parte), e só depois se ramifica em: **pergunta comum** (mapeia pra um template de consulta pré-validado, um por grupo de métricas da seção 22 — rápido, previsível, reaproveita a lógica de negócio já testada), **pergunta aberta** (SQL gerado pela IA, mas nunca contra o schema bruto — só contra uma camada/view read-only com as colunas de negócio já calculadas, pra não deixar o LLM inventar join ou recalcular `STATUS_PAGTO` errado) e **pergunta conceitual** (não toca o banco, busca a definição direto neste documento). O filtro de permissão é sempre injetado por fora, no código que monta a query final — nunca deixado a critério do modelo. **Primeira entrega (2026-07-18, escopo: só pergunta comum)** — camada de tradução pergunta → grupo → função:
> - **`src/lib/ia/templates.ts`** — registro central `TEMPLATES` (mesmo padrão de `graficos-registry.ts`/`comportamental-grupos-registry.ts`): cada grupo de métrica é um `IaTemplate` com `descricaoParaLLM` (quando a tool deve ser escolhida), `parametrosSchema` (JSON Schema dos parâmetros que a Claude extrai da pergunta) e `resolverEExecutar` (resolve nomes → códigos, aplica RLS, chama a função de query já existente da tela — nunca duplica lógica). A trava de RLS é estruturalmente obrigatória aqui: toda função de query chamada dentro de `resolverEExecutar` exige `Scoped<T>` (seção 21.17) — um template que esquecesse de chamar `applyAccessScope`/`resolveComercialParam` simplesmente não compilaria.
>   - **11 templates prontos (2026-07-18), cobrindo os 15 grupos "respondíveis" da seção 22** — `comissoes`, `comercial_visao_geral` (consolida Valores e Totais + Contagens de cedentes + Taxas e Prazos + Tickets num só template com parâmetro `metrica`, já que os 8 números vêm da mesma tela Comercial - Visão Geral com o mesmo filtro único de comercial), `carteira_clientes` (Cards de Risco + Cedentes), `tranche`, `liquidez`, `recompra`, `vop` (Cedente/Sacado via parâmetro `tipo`), `carteira_sacados` (Risco Sacado e Concentração + Maior Concentração + Quantidade de Sacados), `tarifario`, `operacoes`, `borderos_liberados`. **Consolidação deliberada**: menos tools do que grupos sempre que vários números vêm da mesma tela com os mesmos parâmetros — reduz a chance do roteador escolher a tool errada e mantém o prompt mais barato. **"Grupo Econômico" e "Auxiliares" ficaram de fora de propósito** — são dimensões de filtro/cascata (cadastro), não perguntas que alguém faz diretamente; "Comportamental (Acumulado)" também não virou template à parte — é o guarda-chuva dos grupos que já têm template próprio (Tranche/Liquidez/Recompra/VOP/Tarifário/Operações).
>   - **Convenção de formatação**: templates de agregado (sem tabela — liquidez, recompra, vop, tarifário, operações, e as métricas de `comercial_visao_geral`) devolvem os valores já formatados como texto (`R$ 1.234,56`, `12,34%`, `5,20 dias`) numa única linha, em vez de números crus — evita a UI ter que adivinhar se um número é dinheiro, percentual ou dias (cada grupo tem sua própria convenção de unidade, documentada nas interfaces `XxxTotais` de cada query file). Templates com tabela (comissões, carteira de clientes/sacados, tranche, borderôs liberados) continuam devolvendo `linhas`/`totais` crus, que a UI já sabe formatar.
> - **`src/lib/ia/entity-resolver.ts`** — traduz nomes soltos ditos na pergunta ("o Loureiro", "a Root Brasil") pros códigos reais (`COD_OPERADOR_INDICANTE`/`CLIFOR`), reaproveitando as mesmas fontes de busca já usadas nos filtros de tela (`getOperadoresIndicante`, `searchClifor`) — nenhuma busca nova. Devolve `"ambiguo"` com as opções encontradas em vez de adivinhar quando o nome bate com mais de um cadastro.
> - **`src/lib/ia/router.ts`** — `classificarPergunta(pergunta)`: uma única chamada à API da Claude com Tool Use — cada `IaTemplate` vira uma tool; a Claude decide qual (se alguma) responde a pergunta e já devolve os parâmetros extraídos na mesma chamada, sem passo de classificação separado do de extração. Se nenhuma tool for chamada, cai em "aberta" (pergunta aberta/conceitual, ainda não implementadas nesta entrega). **Modelo: `claude-haiku-4-5`** (decisão explícita do cliente em 2026-07-18 — produto ainda em desenvolvimento, sem receita, prioridade é custo mínimo; ~5x mais barato que Opus 4.8 e adequado aqui porque é classificação + extração sobre um conjunto fixo de tools, não raciocínio aberto; sem `thinking`/`effort` — Haiku 4.5 não aceita nenhum dos dois). Reavaliar o modelo quando "pergunta aberta" (SQL gerado) for implementada — essa etapa exige mais capacidade de raciocínio.
> - **`src/app/api/ia/pergunta/route.ts`** (POST) + **`src/components/dashboard/ia/chat-ia.tsx`** — a tela de chat em `/dashboard/ia` já está funcional: bolhas de usuário/IA, sugestões de pergunta clicáveis, tabela de resultado com totais/fonte/aviso de ambiguidade, e tratamento específico pra `Anthropic.AuthenticationError` (mensagem clara "módulo ainda não configurado" em vez de erro genérico, enquanto a chave não é configurada). "Interação por IA" não tem `permissionKey` no menu — só exige sessão válida, mesmo padrão do item de menu.
> - **Dependências**: `@anthropic-ai/sdk` instalado; variável de ambiente `ANTHROPIC_API_KEY` configurada pelo cliente em 2026-07-19 (chave criada em console.anthropic.com — precisou resolver uma recusa inicial de pagamento no billing da Anthropic, cartão travado por antifraude/compra internacional, contornado após liberar o cartão). **Validação ao vivo concluída em 2026-07-19** — pergunta real ("Quanto a Taina recebeu de comissão em junho de 2026?") classificada corretamente pelo roteador (Haiku 4.5, template `comissoes`), nome resolvido pro código do comercial certo, RLS aplicado, consulta real contra o SQL Server, retornando os 3 totalizadores + tabela paginada (50 linhas) — primeiro teste ponta a ponta do módulo, sem ajuste necessário. Ainda **sem síntese de resposta em tom executivo** — a tela mostra o resultado bruto do template (tabela/linha formatada) direto, sem uma 2ª chamada à Claude pra transformar em texto corrido.
> - **Síntese de resposta em texto + eixo de data (2026-07-19, refinamento pedido pelo cliente)** — a resposta padrão de todo template deixou de ser uma tabela/linha crua e passou a ser um `resumo` em texto executivo, com os valores já formatados **em negrito** (markdown simples `**valor**`, renderizado pela UI sem biblioteca de markdown — `renderComNegrito` em `chat-ia.tsx`). ### 19. Regras de negócio centrais (as que a IA e o produto mais vão usar)

#### 19.1 STATUS_PAGTO

| Status | Regra |
|---|---|
| **Vencido** | (`DTPGTO` preenchido + `BANCO` vazio + vencimento < hoje) OU (`DTPGTO` nulo + vencimento < hoje) |
| **A Vencer** | (`DTPGTO` preenchido + `BANCO` vazio + vencimento ≥ hoje) OU (`DTPGTO` nulo + vencimento ≥ hoje) |
| **Pago Em Dia** | `DTPGTO` preenchido + `BANCO` preenchido + vencimento ≥ `DTPGTO` |
| **Pago Vencido** | `DTPGTO` preenchido + `BANCO` preenchido + vencimento < `DTPGTO` |

> Nota histórica: até a v6 da documentação, um bug classificava **qualquer** título com pagamento parcial (`DTPGTO` preenchido + `BANCO` vazio) como `'Vencido'`, sem checar a data de vencimento — títulos com vencimento futuro apareciam como vencidos assim que recebiam pagamento parcial. Corrigido na v7 comparando a data de vencimento com `GETDATE()` também nesse cenário. **Na plataforma Web, implementar direto com a regra correta acima.**

> **"Vencimento" = `CAST(SIGFIDC.DATA AS DATE)`.** Confirmado pelo script SQL de origem que alimenta o Power BI (colado pelo cliente em 2026-07-12): a coluna `DATA` é usada como `VENCIMENTO` em toda a classificação de `STATUS_PAGTO` e no cálculo de `DIAS_ATRASO`/`ATRASO_VENCIDOS` — **não** `VCTO_`. Uma hipótese anterior (`COALESCE(novadata, VCTO_)`) chegou perto do valor certo só porque `DATA` e `VCTO_` coincidem em ~99% das linhas — não é a regra real e foi descartada. Com `DATA`, o card "A Vencer - Cedente" bate exato com o Power BI (R$ 126.576.117,42).

#### 19.2 TIPO_PAGAMENTO

| Tipo | Regra |
|---|---|
| Pagamento Pendente | `DTPGTO` nulo + `BANCO` vazio |
| Pagamento Parcial | `DTPGTO` preenchido + `BANCO` vazio |
| Pagamento Total | `DTPGTO` preenchido + `BANCO` preenchido |

#### 19.3 JUROS_MENSAL

Juros compostos convertidos de período para taxa mensal:

```
(1 + JUROS / VALOR) ^ (30 / (PRAZO + FLOT)) - 1
```

Retorna `NULL` quando `PRAZO + FLOT = 0`, `VALOR = 0`, ou a base é ≤ 0. `JUROS`, `VALOR`, `PRAZO`, `FLOT` vêm de `SIGFLS`.

> **Join com SIGFLS: `SIGFLS.CTRL_ID = SIGFIDC.SIGFLS`.** Confirmado pelo script SQL de origem (2026-07-12) — `SIGFIDC` tem duas colunas parecidas, `SIGFLS` e `CTRL_ID`, que **não são a mesma coisa**: `SIGFIDC.SIGFLS` é a chave estrangeira correta para `SIGFLS.CTRL_ID` (99,997% de match), enquanto `SIGFIDC.CTRL_ID` é outra coisa (só 74% de match coincidente, o suficiente pra mascarar o erro sem chamar atenção). Usar `SIGFIDC.CTRL_ID` no lugar de `SIGFIDC.SIGFLS` foi um erro cometido numa versão anterior da Web e distorceu Taxa Média Geral/Estoque (2,16%/2,11% calculado vs 2,26%/2,04% real).

#### 19.4 estoque_vencido e ATRASO_VENCIDOS

- **estoque_vencido**: `'Sim'` quando `DTPGTO > VENCIMENTO`, ou `DTPGTO` nulo e vencimento < hoje.
- **ATRASO_VENCIDOS**: reusa `DIAS_ATRASO` (calculado via `CROSS APPLY`) para classificar em `'Vencido -5 dias'` (≤ 5 dias) ou `'Vencido +5 dias'` (> 5 dias).

#### 19.5 StatusTranche e DataFuturaTranche

Calculadas no SQL via CTE `PrazoTranche` (deduplicada por `ROW_NUMBER`) e `OperadorComercial`/`SigborsOperador`. **`DataFuturaTranche` = `DATEADD(DAY, ISNULL(CADCRED.PrazoLimiteConfirmacaoDeTitulos, 0), CAST(SIGBORS.DATA AS DATE))` via `SIGFIDC.BORDERO`** — confirmado pelo script SQL de origem colado pelo cliente em 2026-07-16 (versão completa da query de origem, com todas as colunas calculadas). `StatusTranche` compara `DataFuturaTranche` com `GETDATE()` ("A Vencer" se `>=` hoje, senão "Vencido").

> **Correção 2026-07-16 — bug real em produção**: a implementação Web original (`comportamental-tranche.ts`, "Tranche" do Comportamental, e a primeira versão de Exposição Cedente) usava `DATEADD(DAY, CADCRED.PrazoLimiteConfirmacaoDeTitulos, CAST(SIGFLS.DTBORDERO AS DATE))` — **sem `ISNULL`** e com `SIGFLS.DTBORDERO` no lugar de `SIGBORS.DATA`. Quando `CADCRED.PrazoLimiteConfirmacaoDeTitulos` é `NULL` pro cedente (não é raro — ex: cedente 249/UZUCLEAN), `DATEADD(DAY, NULL, ...)` retorna `NULL`; a comparação `NULL >= GETDATE()` nunca é verdadeira, e o `CASE` cai no `ELSE` — classificando **todos** os títulos de tranche daquele cedente como "Vencido", mesmo quando deveriam ser "A Vencer". Medido no grupo Tranche do Comportamental: 25 títulos que apareciam como "Vencido" viraram "A Vencer" após a correção. Descoberto durante validação da coluna "Vencimento Tranche" de Exposição Cedente (ficava sempre vazia pro cedente 249) — corrigido nos dois lugares no mesmo dia. Qualquer nova query que precise de `DataFuturaTranche`/`StatusTranche` deve seguir a fórmula corrigida acima, nunca a antiga.

#### 19.6 Módulo Comissões

- ~~**Tipo_Comissao**: `CODIGO` (texto) igual a `099`, `108`, `010`, `033`, `078` ou `080` → `Interno`; demais → `Externo`.~~ Regra histórica do Power BI, nunca implementada na Web — **substituída** pela tabela `usuarios` (ver nota "Interno/Externo deixou de vir do SIGVEN" abaixo).
- **TAXA_COMISSAO** (faixas sobre `JUROS_MENSAL`, não sobre `JUROS` bruto) — **válida só para Comercial + Interno**; Externo usa `SIGBORS.COMISSAO` (ver nota "Comercial + Externo usa SIGBORS.COMISSAO" abaixo):

  | Faixa de JUROS_MENSAL | Taxa de comissão |
  |---|---|
  | nulo/vazio | 0% |
  | 0% a 2,1% | 3% |
  | 2,1% a 2,29% | 4% |
  | 2,29% a 2,39% | 5% |
  | acima de 2,39% | 6% |

- **VALOR_COMISSAO** = `JUROS` (valor bruto) × `TAXA_COMISSAO`.
- **comissao_comercial** soma `VALOR_COMISSAO` apenas para linhas com `COD_COMERCIAL` preenchido.

> **TAXA_COMISSAO não é fixa em código — é editável pelo cliente.** Existe uma tela própria (`/dashboard/faixas-comissao`, permissão `gerenciar_faixas_comissao`, admin) que gerencia as faixas acima como registros CRUD, persistidos em **MySQL** (Prisma, model `FaixaComissao`: `jurosMin`, `jurosMax` nullable, `taxa`), não no SQL Server. A tabela acima é só o valor-semente original — a fonte de verdade em runtime é essa tabela. **Armadilha de escala confirmada em 2026-07-16**: `jurosMin`/`jurosMax`/`taxa` em `FaixaComissao` são guardados em escala **percentual crua** (`2.1` = 2,1%, `3` = 3%; `faixas-comissao-table.tsx` só concatena `%`, nunca multiplica por 100), enquanto `JUROS_MENSAL` no SQL Server é uma **fração** (`0.0226` = 2,26%). Comparar os dois direto sem converter dá bracket errado silenciosamente. A query de Comissões (`src/lib/db/queries/comissoes.ts`) resolve assim: busca as faixas atuais no MySQL primeiro (`prisma.faixaComissao.findMany`), monta um `CASE` dinâmico comparando `JUROS_MENSAL * 100` (convertido pra escala percentual) contra os limites, com cada limite/taxa como parâmetro nomeado (nunca concatenado na string); o resultado da coluna "Faixa de Comissão" fica em escala percentual (não multiplicar de novo ao formatar), e o cálculo de `VALOR_COMISSAO` precisa dividir por 100 (`desagio * faixaComissao / 100.0`). Qualquer nova query que precise de `TAXA_COMISSAO` deve seguir o mesmo padrão — nunca hardcodar as faixas da tabela acima em SQL.

> **Comercial + Externo usa SIGBORS.COMISSAO, não as Faixas de Comissões dinâmicas (correção 2026-07-18).** As Faixas de Comissões (tabela acima, `FaixaComissao`/MySQL) são exclusivas de Comercial + **Interno**. Pra Externo, a "Faixa de Comissão" de cada título é o campo `SIGBORS.COMISSAO` (já em escala percentual crua, mesma escala de `FaixaComissao` — ex: `6` = 6%) **do borderô daquele título** — ou seja, o mesmo indicante/operador pode ter faixas diferentes em títulos diferentes, dependendo do borderô. `NULL`/sem valor = 0 (sem comissão nesse borderô — confirmado com o cliente que `0` é um valor legítimo, presente em ~41% dos borderôs de forma consistente ao longo dos anos, não é "campo não preenchido"). Quem determina Interno vs. Externo continua sendo a tabela `usuarios` (ver nota abaixo) — Externo é tanto quem está cadastrado como Comercial+Externo quanto qualquer código de indicante/operador sem cadastro algum. Implementado em `buildFaixaComissaoExpr()`/`buildInternoCondicao()` (`src/lib/db/queries/comissoes.ts`), reaproveitado por `graficos-comissoes.ts` (só troca o alias de SIGBORS — `SB` em Comissões, `B` em Gráficos — e a expressão de código do comercial, `OC.codigoComercial` vs. `COMERCIAL_EXPR`). Validado contra o SQL Server real em 2026-07-18: comercial Interno manteve os valores idênticos a antes da mudança (comprovando que o cálculo de Interno não foi afetado); comercial Externo passou a usar exatamente o valor cru de `SIGBORS.COMISSAO` por borderô, conferido título a título.

> **Interno/Externo deixou de vir do SIGVEN — vem da tabela `usuarios` (correção 2026-07-17).** A regra antiga do Power Query M do Power BI (`Tipo_Comissao`: `CODIGO IN ("099","108","010"/"033","078","080")` → `"Interno"`, senão `"Externo"`) nunca chegou a ser implementada na Web e foi descartada por decisão explícita do cliente ("Essa parte que define o que é Interno e o que é externo deixa de existir, e o que informa esses novos dados é a tabela de usuários"). Fonte de verdade agora: `Usuario` (Prisma/MySQL) com `perfil = "Comercial"` — `comercialCodigo` (o código do indicante/operador, mesmo valor de `COD_OPERADOR_INDICANTE`) mapeado pra `comercialTipo` ("Interno"/"Externo"). Um código de indicante/operador **sem usuário correspondente cadastrado é automaticamente "Externo"**. Implementado em `getTipoComercialMap()`/`applyTipoComercial()` (`src/lib/db/queries/comissoes.ts`) — a resolução acontece em **JavaScript, não em SQL** (busca os comerciais Interno cadastrados via Prisma, monta um `Map<comercialCodigo, comercialTipo>`, aplica sobre as linhas já retornadas do SQL Server usando `OC.codigoComercial`, a mesma coluna crua da `SigborsOperador` CTE — não confundir com `indicanteOperador`, que já vem formatado "código - nome"). Alimenta a nova coluna **"Tipo"** do Relatório de Comissões (tabela e exportação Excel), entre "Indicante/Operador" e "Data da Compra" — mostra "—" quando o título não tem indicante/operador nenhum. **Escopo desta correção**: só a coluna Tipo passou a refletir a nova fonte; o CÁLCULO da comissão (Faixas de Comissões) permanece igual para todo mundo, Interno ou Externo, até o cliente definir a regra específica de Externo (decisão explícita do cliente: manter o cálculo atual como valor provisório pra Externo, não zerar) — validado que os valores de Comissão/Faixa de Comissão não mudaram após a correção. **Atualização 2026-07-18**: a regra de Externo chegou e foi implementada — ver nota "Comercial + Externo usa SIGBORS.COMISSAO" logo acima. O cálculo de Externo deixou de ser o provisório (mesma Faixa de Comissões do Interno) e passou a usar `SIGBORS.COMISSAO`.

#### 19.7 RISCO (CADCRED)

Soma de `VALOR_` (SIGFIDC) para títulos em qualquer situação de risco (vencido, a vencer, pendente), calculada via subquery correlacionada por `CLIFOR`, respeitando o mesmo filtro `CODIGO IN (040, 041, 042, 046)`.

#### 19.8 Carteira de Clientes — universo de cedentes e colunas

Módulo implementado na Web (`/dashboard/carteira-clientes`) como tabela paginada/ordenável com os mesmos componentes do Relatório Analítico de Títulos (cards totalizadores, filtros em popup, exportação Excel, envio por e-mail, modal de detalhe).

**Universo de cedentes** — `CADCRED` sozinha **não é suficiente** como tabela-guia: existem cedentes com exposição real em `SIGFIDC` (títulos com `CODIGO IN (040, 041, 042, 046)`) mas sem registro algum em `CADCRED`. Um `FROM CADCRED LEFT JOIN ...` convencional perde esses cedentes silenciosamente — no ambiente de produção isso descartava 2 cedentes com R$2,17M de exposição real, distorcendo o total de "Risco" (R$138,73M calculado vs R$140,90M correto). A regra confirmada com o cliente (ver decisão em 21.8) é:

```sql
Universo AS (
    SELECT clifor FROM CADCRED
    UNION
    SELECT CLIFOR FROM SIGFIDC WHERE CODIGO IN (040, 041, 042, 046)
)
```

Todo o restante da query (CADCRED, SIGCAD, SIGVEN, GrupoEmpresa etc.) faz `LEFT JOIN` a partir de `Universo`, nunca o contrário.

**Colunas da tabela** (mapeamento DAX/fonte → SQL):

| Coluna | Origem |
|---|---|
| Código | `Universo.clifor` |
| Cedente | `SIGCAD.NOME` |
| Comercial | `CADCRED.gerenteconta` → `SIGVEN` (comercial **por cedente**, diferente do `COD_OPERADOR_INDICANTE` por borderô usado em Títulos — ver 21.9) |
| Situação | `SIGCAD.BLOQUEIO` traduzido — ver mapeamento abaixo |
| Limite de Crédito | `CADCRED` |
| Risco Cedente | `SUM(SIGFIDC.VALOR_)` agrupado por `CLIFOR`, mesmo filtro de códigos |
| Participação Cedente | Risco Cedente ÷ soma total do Risco de todos os cedentes |
| Limite Disponível | Limite de Crédito − Risco Cedente |
| Vencido | `SUM(SIGFIDC.VALOR_)` onde `STATUS_PAGTO = 'Vencido'` (19.1), por `CLIFOR` |
| A Vencer | `SUM(SIGFIDC.VALOR_)` onde `STATUS_PAGTO = 'A Vencer'`, por `CLIFOR` |
| Data do Último Borderô | `MAX(SIGBORS.DATA)` via `SIGFIDC.BORDERO`, por `CLIFOR` |
| Tranche | `tranche_tomada` — A Vencer + títulos com `ESTADOCONFIRMACAOTITULO.DESCRICAO = 'A Confirmar'` |
| Taxa | `CADCRED.TAXA` (`FATORFIDC / 100.0`) |
| Método | `CADCRED.METODOCALCULOFIDC` traduzido — ver mapeamento abaixo |

**apoio_cliente_risco** — coluna de apoio (não exibida) usada para esconder linhas totalmente zeradas: `limite_credito + risco + limite_disponivel + a_vencer + vencido + tranche_tomada + 0`, filtrando `<> 0`.

**Filtros** — Comercial (`CADCRED.gerenteconta`), Grupo Econômico (`GrupoEmpresa` ∪ `cadGrupoEmpresarial`, deduplicado por `clifor` via `ROW_NUMBER`) e Cedente, entregues no mesmo padrão de popup separada do Relatório Analítico de Títulos (ver 21.10). A lista de cedentes para o filtro precisa ser a mesma `Universo` (não só `SIGFIDC.CLIFOR`), senão os 2 cedentes órfãos ficam inexistentes/inalcançáveis no filtro.

Fica sempre visível ao lado do botão de filtros (não dentro da popup), e o valor selecionado é exibido como título centralizado na barra superior da tela.

### 21. Decisões de negócio e notas técnicas (herdadas do Power BI, válidas para a Web)

1. **CADCRED separada da SIGFIDC** — mantida como tabela independente para preservar cedentes sem título ativo. Um JOIN direto causaria perda desses cedentes, distorcendo métricas de limite total. Na Web: nunca colapsar essas duas fontes em uma única query sem UNION/OUTER JOIN cuidadoso.
2. **Slicer "Visão"** — no Power BI, uma tabela estática sem relacionamento, controlando um comportamento "Todos / Com Risco / Sem Risco" via `SELECTEDVALUE`. Na Web, vira um filtro de contexto de aplicação (ex: querystring ou state global), com fallback padrão para "Todos".
3. **Códigos SIGFIDC considerados** — `WHERE F.CODIGO IN (040, 041, 042, 046)`. Todo endpoint/query que toque `SIGFIDC` deve herdar esse filtro por padrão.
4. **Padrão SIGBORS e filtros de segmentação** — medidas/consultas baseadas em `SIGBORS` não herdam automaticamente filtros de Comercial/Grupo Econômico/Cedente aplicados sobre `SIGFIDC` (por causa do relacionamento `*:*`). O padrão é capturar o conjunto de `BORDERO` já filtrado em `SIGFIDC` e então filtrar `SIGBORS` por esse conjunto explicitamente.
5. **Performance em listagens grandes** — o equivalente Power BI usava uma medida de "top N condicional" como guarda para não carregar a tabela sem filtro algum. Na Web, replicar como paginação obrigatória + exigência de ao menos um filtro de contexto (Comercial, Grupo Econômico Cedente ou Cedente) antes de consultas pesadas.
6. **Relacionamento SIGFLS↔Dcalendario** — no Power BI ficava inativo por padrão, ativado pontualmente em uma medida (`USERELATIONSHIP`). Na Web, isso não é uma restrição técnica real — é uma regra de negócio: por padrão, os acumulados usam a data de referência do filtro corrente; o uso de `DTBORDERO` como data alternativa é uma opção secundária, não o padrão.
7. **Preparação para IA/RAG** — nomes de colunas, tabelas e regras devem permanecer descritivos e consistentes (evitar abreviações ambíguas) para facilitar indexação e recuperação semântica pelo assistente de IA da plataforma.
8. **`Universo` (CADCRED ∪ SIGFIDC.CLIFOR) como tabela-guia** — aplicação concreta da regra do item 1 em Carteira de Clientes (19.8): usar só `CADCRED` como driving table exclui cedentes com exposição real em `SIGFIDC` mas sem registro em `CADCRED`. Confirmado com o cliente (recomendação aceita) que esses cedentes órfãos **devem** aparecer na carteira. Padrão a repetir sempre que uma tela precisar "todo cedente com alguma relação com a FIDC", não só "todo cedente cadastrado em CADCRED".
9. **Comercial por cedente vs. Comercial por borderô** — `CADCRED.gerenteconta` (usado em Comercial - Visão Geral e Carteira de Clientes, grão por cedente) e `COD_OPERADOR_INDICANTE` via `SIGBORS`/`SIGVEN` (usado no Relatório Analítico de Títulos, grão por borderô/título) são **dois vínculos diferentes para duas granularidades diferentes** e não devem ser confundidos ou unificados numa única coluna "Comercial" genérica.
10. **Filtros em popup separada** — histórico: era o padrão original de Relatório Analítico de Títulos, Carteira de Clientes, Comportamental e Comissões. Os filtros abriam numa janela `window.open` própria (não um painel na mesma página), que devolvia o resultado via `postMessage` (`{origin: window.location.origin}`) para a janela principal ao clicar em "Aplicar filtros". **Migrado por completo pra filtro retrátil em 2026-07-16** (ver 21.16 abaixo) — as 5 telas com filtro (Borderôs Liberados, Títulos, Carteira de Clientes, Comportamental, Comissões) agora usam o mesmo `RetractableFiltrosPanel`. Todas as rotas de popup (`/titulos-filtros`, `/carteira-clientes-filtros`, `/comportamental-filtros`, `/comissoes-filtros`) e os respectivos `*-filtros-button.tsx`/`filtros-*-popup.tsx` foram removidos (código morto), inclusive do `middleware.ts`. Nenhuma tela nova deve voltar a usar popup — o padrão retrátil é o único válido daqui pra frente.
11. **Rótulo "código - nome" em selects de entidade** — todo filtro que seleciona uma entidade cadastrada (Comercial, Grupo Econômico, Cedente, Sacado) deve exibir o código junto ao nome no rótulo da opção, ex.: `110 - ROOT BRASIL`. Nome sozinho não é suficiente para diferenciar cadastros duplicados ou ambíguos — bug identificado e corrigido em produção depois de passar sem validação no filtro de Grupo Econômico.
12. **CTE referenciada múltiplas vezes = custo multiplicativo (SQL Server 2008)** — quando uma derived table/CTE encadeada (ex.: `FiltroClifor` → `Universo` → `BorderosBase` → `SigborsBase`) é referenciada mais de uma vez na mesma query (ex.: uma CTE separada por janela de data, todas somadas via `CROSS JOIN`), o otimizador do SQL Server 2008 reinlina e reexecuta a cadeia inteira a cada referência, em vez de reaproveitar o resultado. Medido em 2026-07-16 no grupo Operações do Comportamental: 1 referência ≈ 400ms, 2 referências ≈ 7s, 4 referências → timeout (>20s), mesmo com tabelas pequenas envolvidas (SIGBORS tem ~28 mil linhas). **Correção**: consolidar todas as janelas/variações num único `SELECT` sobre a CTE de base, usando `SUM(CASE WHEN <condição> THEN valor ELSE 0 END)` por janela em vez de uma CTE + `CROSS JOIN` por janela — reduz pra ~200ms. `OPTION (RECOMPILE)` **não** resolve esse padrão específico (testado, sem efeito). Sempre que uma nova query precisar da "mesma métrica em N variações de filtro/data" sobre a mesma base, usar SUM condicional numa única passada, nunca N CTEs somadas por CROSS JOIN.
13. **CTE com `UNION` referenciada por uma query externa também é armadilha (SQL Server 2008)** — variante do item 12, mais sutil: aqui a CTE só é referenciada **uma vez**, mas ela mesma é definida com `UNION` (duas ramas de tabelas diferentes) e é usada dentro de um `JOIN` ou `IN (SELECT ... FROM cte)` a partir de outra tabela. Medido em 2026-07-15 no filtro em cascata de Grupo Econômico do Comportamental: a `UNION` isolada (`SELECT idgrupo FROM GrupoEmpresa JOIN CADCRED ... UNION SELECT idgrupo FROM GrupoEmpresa JOIN SIGFIDC ...`) roda em ~380ms; a mesma lógica virando uma CTE e sendo referenciada por fora (`cadGrupoEmpresarial CG JOIN GruposDoComercial` ou `CG.ID IN (SELECT idgrupo FROM GruposDoComercial)`, driving table de só 267 linhas) sobe pra 11-14s. **Correção**: quando o lado "many" da relação for pequeno o bastante pra caber em memória (aqui, no máximo algumas centenas de IDs), não deixe o SQL Server juntar as duas coisas numa query só — rode a `UNION` isolada (rápida) primeiro, pegue os IDs num array, e filtre a lista já carregada (ex.: `getGruposEconomicos()`, cacheada) em JavaScript. Ver `comportamental-grupos-economicos.ts`.
14. **Filtros em cascata (Comercial → Grupo Econômico → Cedente/Sacado)** — padrão de UX estabelecido em 2026-07-15, replicado nas 3 telas com popup de filtros (Comportamental, Carteira de Clientes, Relatório Analítico de Títulos): ao escolher um filtro "de cima" (ex. Comercial), os selects "de baixo" (Grupo Econômico, Cedente, Sacado) recarregam mostrando só as opções compatíveis, e se o valor já selecionado deixar de existir na lista filtrada, a seleção é limpa automaticamente (o que propaga a cascata adiante). Cada tela tem endpoints dedicados para as listas em cascata (nunca reaproveitar um endpoint sem filtro que outra tela já usa sem parâmetros — ex. `/api/relatorio-titulos/grupos-economicos` continua servindo a lista completa pra quem não filtra). Em Títulos, Comercial cascateia para **dois** pares independentes (Grupo Econômico Cedente → Cedente, e Grupo Econômico Sacado → Sacado), já que a tela tem os dois universos ao mesmo tempo; o filtro de Sacado (busca sob demanda, não lista fixa) recebe os filtros de cascata como parâmetros extras na própria busca, sem lista pra "cair fora" — por isso não é limpo automaticamente, só passa a buscar dentro do escopo já filtrado.
15. **PDFs sempre mostram o contexto de filtro** — padrão confirmado pelo cliente em 2026-07-15, válido pra toda geração de PDF na plataforma (não só Comportamental), a menos que ele peça algo diferente pra um caso específico: todo PDF exportado exibe uma caixa logo abaixo do título/subtítulo informando se os dados vieram filtrados ou não — nunca omite essa informação. Filtrado: caixa em tom avermelhado (`#FBEAEC`/`#B3495A`) com "Filtros aplicados: {resumo}". Sem filtro: caixa neutra (`#F7F8FA`/`#6B7280`) com "Sem filtros aplicados — dados de toda a carteira." Implementado em `buildGroupPdfBuffer` (`src/lib/exports/group-pdf.ts`) — qualquer novo builder de PDF deve seguir o mesmo padrão (nunca deixar quem recebe o arquivo em dúvida sobre a origem dos números).
16. **Cache curto (2 min) nos dados de cards/tabelas + bypass no "Atualizar" + indicador persistente de última atualização** — decisão do cliente em 2026-07-16: navegar entre módulos deve parecer instantâneo (sem esperar consulta nova toda vez), mas o botão "Atualizar" do topbar precisa sempre trazer dado fresco do SQL Server. Implementado com três peças que sempre andam juntas:
    - **Servidor**: `withCache` (`src/lib/db/cache.ts`), já usado nas listas de filtro (15min), ganhou um `DATA_CACHE_TTL_MS` e um parâmetro `forceRefresh` que ignora o cache e regrava o valor novo. Toda query de card/tabela (Comercial - Visão Geral, Relatório de Títulos, Carteira de Clientes, todos os grupos do Comportamental) passou a ser envolvida em `withCache`, com a chave incluindo todos os parâmetros que mudam o resultado (filtros serializados via `JSON.stringify`, mais página/ordenação nas tabelas). Cada `getXxx(...)` ganhou um parâmetro final opcional `forceRefresh = false`; cada rota de API lê `searchParams.get("refresh") === "1"` e repassa. TTL ajustado de 20s pra **2 minutos** em 2026-07-16, a pedido do cliente ("não precisamos desse nível de atualização... quanto mais rápida e veloz for o carregamento das telas, melhor") — o botão "Atualizar" continua bypassando o cache, então dado sob demanda nunca é bloqueado pelo TTL maior.
    - **Cliente (bypass)**: `useIsForcedRefresh(refreshToken)` (`src/components/dashboard/refresh-context.tsx`) — hook que retorna `true` só no ciclo de fetch imediatamente seguinte a um clique em "Atualizar" (nunca na montagem inicial nem quando só o filtro muda), comparando o `refreshToken` atual com o valor guardado de um render anterior via `useRef`. Todo componente que busca dados de card/tabela chama esse hook e, quando `forced` é `true`, acrescenta `?refresh=1` na URL da requisição (além de incluir `forced` nas dependências do `useEffect`).
    - **Cliente (indicador "Atualizado em ...")**: o `RefreshProvider` mantém `lastUpdated` persistido em `localStorage` (chave `sbk:last-updated`), restaurado no mount — sobrevive a fechar o navegador/app e voltar depois, como pedido pelo cliente ("mesmo saindo da aplicação... a informação precisa ser vista"). É atualizado via helper `markUpdated()` **só** no clique em "Atualizar" (após o spinner mínimo). `RefreshButton` exibe sempre (não só em telas largas) a data + hora completas: `Atualizado em DD/MM/AAAA HH:MM:SS`. Uma primeira versão também atualizava esse timestamp em toda navegação entre telas (`usePathname()` mudando) — revertido em 2026-07-16 a pedido do cliente: dava a falsa impressão de que o banco era consultado a cada troca de menu, quando na prática a navegação só bate no banco se o cache daquela tela/filtro já tiver expirado. O indicador agora significa "última atualização manual", com a garantia implícita (pelo TTL) de que os dados nunca têm mais de 2 minutos de idade mesmo sem clicar em nada.
    - Validado (2026-07-16): 1ª chamada bate no banco; 2ª chamada com os mesmos filtros retorna em ~0ms (cache); chamada com `forceRefresh` volta a bater no banco; filtros diferentes geram uma entrada de cache diferente (nunca retornam dado errado pro filtro pedido).
    - Sempre que uma nova tela/query de card ou tabela for criada, ela **precisa** seguir esse mesmo padrão (`withCache` + `forceRefresh` no servidor, `useIsForcedRefresh` + `?refresh=1` no cliente) — não deixar nenhuma consulta "escapar" do cache curto, senão ela nunca vai se sentir tão rápida quanto as demais ao navegar.
17. **Trava de acesso por perfil — Comercial/Cedente/Sacado só veem os próprios dados (implementada 2026-07-18).** Pedido do cliente: um usuário Comercial (Interno ou Externo) vinculado a um código de indicante/operador (`COD_OPERADOR_INDICANTE`) só pode ver os títulos/dados **daquele código**, nunca de outro comercial — "um comercial não pode ver os dados de outro". Estendido pelo cliente na mesma conversa pra também cobrir os perfis Cedente (restrito ao próprio `CLIFOR`) e Sacado (restrito ao próprio código de sacado). Três peças:
    - **Vínculo no cadastro** — já existia antes desta correção: `Usuario.comercialCodigo` (perfil Comercial, código cru) e `Usuario.vinculo` (perfil Cedente/Sacado, rótulo completo "CÓDIGO - NOME - CGC" escolhido no `CliforSelect`, mesmo campo que já alimentava o texto "Cedente/Sacado vinculado" na revisão do cadastro). `extractVinculoCodigo`/`extractVinculoNome` (`src/lib/usuarios/vinculo.ts`) isolam o código e o nome desse rótulo.
    - **Sessão carrega o vínculo** — `comercialCodigo`/`vinculoCodigo`/`vinculoNome` adicionados ao JWT/`Session` (`src/lib/auth.ts`, tipos em `src/types/next-auth.d.ts`), resolvidos no login e recalculados no `trigger: "update"`. A conta administrativa via variável de ambiente nunca seta esses campos (fica sempre irrestrita, `role: "Administrador"`).
    - **Trava real no servidor** — `getAccessScope(session)`/`applyAccessScope(filtros, session)`/`resolveComercialParam(raw, session)` (`src/lib/auth/access-scope.ts`): perfil Comercial força `filtros.comercial`; Cedente força `filtros.cedente`; Sacado força `filtros.sacado` — **sempre sobrescrevendo** o que veio da query string ou do corpo do POST, nunca confiando no cliente. Chamado logo após `parseFiltrosFromSearchParams`/receber o body, antes da query rodar — em **todas** as rotas de API que retornam dado (GET principal, `/export`, `/export/email`, `/exportar-pdf*` e `/exportar-pdf*/email` de todo módulo, os 8 cards de Comercial - Visão Geral via `resolveComercialParam`, e os ~24 endpoints de cascata de filtro — `grupos-economicos*`/`cedentes`/`sacados`). **Falha fechada**: perfil que exige vínculo (Comercial/Cedente/Sacado) mas está sem nenhum cadastrado (`comercialCodigo`/`vinculoCodigo` nulo — só deveria acontecer se alguém criar o usuário direto via API, contornando a validação obrigatória do formulário) recebe um código-sentinela (`__sem_vinculo__`) que nunca bate com nada real, em vez de ficar sem filtro nenhum — a alternativa (deixar passar irrestrito) seria o oposto do pedido do cliente.
    - **Campo travado na tela** — pedido explícito do cliente: o filtro de Comercial/Cedente/Sacado continua **visível**, mas travado (mostra o próprio código/nome, não dá pra trocar), em vez de sumir da UI. `useAccessScope()` (`src/components/dashboard/use-access-scope.ts`, espelha `access-scope.ts` no cliente via `useSession()`) + `<LockedFiltroField>` (`locked-filtro-field.tsx`, cadeado + rótulo) — aplicado nos 9 componentes de filtro retrátil (Títulos, Comissões, Carteira de Clientes, Comportamental, Borderôs Liberados, Carteira de Sacados, Exposição Cedente, Tranche, Gráficos) e no seletor de Comercial da Visão Geral. Cada componente ganhou um `useEffect` que força o estado local pro valor da trava sempre que ela está ativa — garante que efeitos cascata (Grupo Econômico/Cedente/Sacado dependentes do Comercial escolhido) e o resumo de filtros exibido/exportado em PDF já reflitam o valor correto. **A trava da tela é só UX** — o servidor sempre reforça a trava de verdade, mesmo que a tela seja contornada.
    - Validado com testes unitários standalone (`applyAccessScope`/`resolveComercialParam`/`getAccessScope`, sessões simuladas por perfil) em 2026-07-18: Comercial tentando forçar outro código via filtro é ignorado; Cedente idem; Administrador nunca é restringido; perfil sem vínculo cai no sentinela de falha fechada. Validado também ao vivo contra o SQL Server real (comercial 033 tentando explicitamente `comercial=096` na Comissões — resultado continuou travado em 033).
    - **Endurecimento em tempo de compilação (2026-07-18, pensando no módulo de IA/RAG)** — até aqui, a trava dependia de disciplina do desenvolvedor: cada `route.ts` precisa *lembrar* de chamar `applyAccessScope`/`resolveComercialParam` antes de invocar a função de query. Isso era um risco real pro RAG: o roteador de intenção da IA (seção 12, [[project_ia_rag_arquitetura]]) vai chamar essas mesmas funções de query direto, sem passar pela rota HTTP — bastava um template novo esquecer o passo de RLS pra vazar dado de outro comercial/cedente/sacado, sem nenhum aviso até alguém testar o cenário errado. Corrigido transformando esse esquecimento de bug em runtime pra **erro de compilação**: `Scoped<T>` (`src/lib/auth/access-scope.ts`) é um tipo nominal (`T & { readonly [SCOPE_APPLIED]: true }`, marca de símbolo único) que só `applyAccessScope`/`resolveComercialParam` conseguem produzir. Toda função de query que lê dado sensível (as ~24 funções por trás de Comissões/Títulos/Carteira de Clientes/Carteira de Sacados/Exposição Cedente/Tranche/Borderôs Liberados/11 grupos do Comportamental/7 gráficos + os 8 cards do Comercial - Visão Geral) teve o parâmetro de filtros/comercial trocado de `XFiltros`/`string` pra `Scoped<XFiltros>`/`Scoped<string>` — `tsc` agora recusa compilar qualquer chamada que passe um filtros/comercial que não veio de `applyAccessScope`/`resolveComercialParam`, mesmo dentro do próprio backend, nunca só na rota HTTP. As ~24 funções de cascata de filtro (listas de grupos econômicos/cedentes/sacados pra popular dropdown — só nome/código, não dado financeiro) ficaram de fora de propósito, escopo reduzido dado o risco bem menor. Confirmado com um teste de prova de conceito (arquivo temporário, apagado): tentar compilar uma chamada a `getComissoes` passando um `ComissoesFiltros` comum (sem passar por `applyAccessScope`) falha com `Property '[SCOPE_APPLIED]' is missing`. Refletido no `MEMORY.md` do projeto — qualquer função de query nova que leia dado sensível deve seguir o mesmo padrão desde o início, nunca aceitar o tipo de filtros "cru".
